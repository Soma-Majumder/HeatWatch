HeatWatch Agent Architecture

Agent spec · Draft 0.2 · 8 October 2026

HeatWatch: a research agent for NYC heat complaints

HeatWatch answers questions about heat and hot water complaints using New York City's public 311 data. It reads each result and decides which analysis to run next, and every number in its answer traces back to the query that produced it.

1What makes it an agent

An analytics pipeline runs the same steps every time. An agent reads each result and chooses the next step. The word describes who controls the order of work, and three questions settle it.

Who picks the next step?

Pipeline
The code. The order is written in advance.
Agent
The model, after reading the last result.

Can two questions take different paths?

Pipeline
No. Only the numbers differ.
Agent
Yes. Different tools, in a different order.

Can it decide to stop?

Pipeline
It always finishes and always reports.
Agent
It can say it has enough, or that the data cannot answer.

The original project doc named the risk: if HeatWatch always runs the same queries and summarizes them, it is an analytics pipeline. The design below avoids that by giving the model several tools that lead to different places, and by testing that different questions produce different paths.

2One run, end to end

This is what a single question looks like from start to finish. All numbers in this section are made up to show the mechanics. They are not real results.

Mid-January · a Brooklyn council office asks

"Heat complaints in Brooklyn seem way up this winter compared to last winter. Is that true, and where is it coming from?"

  1. Turn the question into something measurable

    "This winter" becomes October 1 to January 15, because heat season starts October 1. "Last winter" becomes the same dates a year earlier. Before counting anything, the agent checks that both periods have complete data.

    check_coverage(type="heat/hot water", borough="Brooklyn",
               periods=[Oct 1–Jan 15 this season, same dates last season])
→ both complete, no missing days

    DecisionData is complete, so continue. Missing days would have ended the run here with "this comparison isn't reliable."

  2. Answer the first half of the question

    compare_periods(borough="Brooklyn", group_by="community_district")
→ Brooklyn: 14,200 → 18,400 complaints (+30%)
  Districts 5 and 17: +2,900 of the 4,200 increase
  The other 16 districts: +8% on average

    DecisionThe rise is real but uneven: two districts hold about 70% of it. Look inside those two first. An even rise would have sent it to the weather check instead.

  3. Try a query that is too big, and get stopped by code

    get_records(districts=[5, 17], period=this_season)
→ rejected: 5,100 rows exceeds the 2,000-row limit; use an aggregate tool

count_buildings(districts=[5, 17], periods=both)
→ buildings with complaints: 590 → 610 (about the same)
  complaints per building: 3.9 → 8.4
  10 buildings account for 2,400 of the increase

    DecisionThe model read the error and switched tools. The finding: about the same number of buildings are complaining, but a handful are complaining far more.

  4. Rule out the obvious alternative

    get_temperature(periods=both)
→ this winter was about 12% colder by heating demand

    DecisionA colder winter raises complaints everywhere by a similar amount. That fits the 8% rise in the rest of Brooklyn, but not the jump in two districts. Weather is a small part of the story.

  5. Draft, then have every claim checked

    The first draft said: "Landlords at these 10 buildings are failing to provide heat."

    Rejected by claim check

    No tool result supports it. Complaints show that tenants reported a problem. They do not prove heat was out or who was at fault, and one building can produce hundreds of repeat calls. The agent rewrote the sentence to say only what the data shows.

  6. Deliver the briefing

    Yes. Brooklyn heat complaints are up 30% (14,200 → 18,400) for Oct 1 to Jan 15 compared with the same dates last season. [ledger #2]

    The rise is concentrated. Community Districts 5 and 17 account for about 70% of it. [#2] The number of buildings with complaints there is about the same as last year, but complaints per building doubled, and 10 buildings account for 2,400 of the increase. [#4] The building list is attached.

    Weather explains a small part. This winter was about 12% colder, which fits the 8% rise elsewhere in the borough but not the jump in these two districts. [#5]

    What this cannot tell you: whether heat was actually out, or why. Complaints are reports, not inspections. A sensible next step is checking city inspection records for these 10 buildings.

    9 steps · 6 queries · 38 seconds · full trace available

The same question with different data

The code is identical in every row. What the data showed decided the path.

First results showedWhat the agent did nextWhere it ended
Rise concentrated in two districtsCounted buildings, then checked weatherA building list with caveats (the run above)
Rise spread evenly everywhereChecked weather first, then compared complaints per cold day"Mostly a colder winter"
Last season missing two weeksStopped"This comparison isn't reliable," with the gap shown
Complaints actually downAnswered and stopped"No, they are down 6%"

Compared with a dashboard

A dashboard would show a 30% rise and a bar chart by district. A person would then have to notice the two tall bars, filter to them, think to count buildings instead of complaints, check the weather, and write it up. A fixed pipeline would run the same three queries for every question, would never count buildings, and would report a 30% rise even if two weeks of data were missing. The agent took the analyst's next steps itself, choosing each one from the last result.

Two facts about this subject shape every tool. One building without heat can produce dozens of complaints, so complaint counts overstate how widespread a problem is. And heat is seasonal: the city's heat season runs October 1 to May 31, with 68°F required indoors by day when it is below 55°F outside and 62°F at night, so comparisons belong on the same dates and similar weather.

3Product requirements

Problem

People who track housing conditions can already see 311 heat complaints on dashboards. Answering "is it worse, where, and why" still takes an analyst hours of filtering, and raw counts mislead: one building can generate hundreds of complaints, and a cold winter raises complaints everywhere. Most people asking these questions are not analysts.

Users

UserWhat they needTypical question
Council staff PrimaryA fast, sourced answer about their district before a hearing or constituent meeting"Are heat complaints up in our district this winter?"
Tenant organizersWhich buildings have concentrated complaints"Is it a few buildings or the whole neighborhood?"
ReportersA quick check of a claim, with numbers they can cite"Is it true complaints doubled in the Bronx?"

Not a user in v1: a tenant who needs heat restored. HeatWatch points them to 311.

Goals

  • Answer comparison and concentration questions in under a minute, with every number sourced.
  • Make every number reproducible from its stored query.
  • Say plainly when the data cannot answer the question.
  • Teach the team the full agent stack: loop, tools, state, limits, evaluation.

Non-goals

  • Deciding the cause of a problem or who is at fault.
  • Predicting future complaints.
  • Complaint types other than heat and hot water.
  • Any action that changes an outside system.
  • Collecting anything about the person asking.

Questions supported in v1

TypeExampleTools usually involved

Functional requirements

FR-1Accept a plain-English question about NYC heat and hot water complaints.
FR-2Turn time phrases into explicit dates and state those dates in the answer.
FR-3Check data coverage before any comparison. Stop and report the gap if coverage is incomplete.
FR-4Choose each next analysis from the previous results, using only the defined tools.
FR-5Compute every number in code. The model interprets numbers and never calculates them.
FR-6Store every result in the evidence ledger with its exact query and fetch time.
FR-7Run the claim check before output. Remove any claim not backed by a ledger entry, and any statement of cause.
FR-8Return a briefing in this order: direct answer, findings with ledger references, limitations, suggested next step.
FR-9When a budget is reached, stop and return partial findings labeled as partial.
FR-10Write a complete trace for every run.

Quality requirements

AreaRequirement
SpeedMedian answer under 45 seconds; hard stop at 120 seconds.
LimitsAt most 12 steps and 8 data queries per question.
CostA per-question spending cap, set during the spike from measured usage.
ReproducibilityThe ledger stores each result as fetched. 311 records are updated after filing, so a rerun on a later date may differ slightly; the briefing states the fetch date.
SafetyNo tool can write to any outside system.

4Technical design

The model makes one kind of decision: what to do next. Everything else is your code, and your code holds every limit.

Components

ComponentResponsibilityImplementation
Loop controllerRuns the model and tool loop; enforces step, query, and time budgetsAbout 80 lines of Python, written by hand
ModelReads state and returns the next tool call or a final draftAny model API with tool calling; low temperature
Tool gateChecks every call against its schema, allowed values, and row and date limitsJSON Schema validation plus allowlists
ToolsBuild queries, run them, compute resultsSmall Python functions; aggregates done by the data source
Evidence ledgerStores every result with its query and fetch timeAppend-only table in SQLite, one file per run
Claim checkMatches every number in the draft to a ledger value; blocks causal languageCode match on numbers plus one model pass to extract claims
Trace logRecords every model call, tool call, and state changeOne JSON Lines file per run
Test runnerRuns the question set and scores each runpytest or a short script, run on every change

Tool contracts

Each tool returns small, computed results, never raw dumps. A rejected call returns an error message the model can act on.

ToolTakesReturnsLimits
check_coverageArea, one or two date rangesDays with records, list of missing days, latest record date, whether the label existsRange up to 2 years
compare_periodsArea, two date ranges, optional grouping (borough, community district, ZIP)Counts per group for both periods, with change and percent change computed in codeUp to 60 groups
count_buildingsArea, two date ranges, top NDistinct buildings, complaints per building, top buildings with countsTop N up to 25
get_temperatureTwo date rangesDaily lows and highs, total heating demand per periodSource to be chosen
get_recordsFiltersRaw rows, for inspecting a few records2,000 rows

Data source

NYC 311 Service Requests on NYC Open Data (dataset erm2-nwe9). Fields confirmed on live records on October 5, 2026: created_date, complaint_type, descriptor, status, incident_address, borough, community_board, bbl (building lot number), latitude, longitude. Aggregates run on the server, so a district comparison returns a few dozen rows instead of thousands.

# compare_periods for Brooklyn by district (one period shown)
GET https://data.cityofnewyork.us/resource/erm2-nwe9.json
  ?$select=community_board, count(*) AS n
  &$where=complaint_type='HEAT/HOT WATER' AND borough='BROOKLYN'
          AND created_date between '2026-10-01T00:00:00' and '2027-01-15T23:59:59'
  &$group=community_board
# label confirmed 8 Oct 2026; check_coverage still verifies it at the start of each run

Investigation state and ledger

The state is what the model sees on each turn. The ledger is what the claim check and the briefing references point to.

{
  "question": "Heat complaints in Brooklyn seem way up this winter...",
  "periods": { "a": ["2025-10-01", "2026-01-15"], "b": ["2026-10-01", "2027-01-15"] },
  "budget":  { "steps_used": 4, "steps_max": 12, "queries_used": 3, "queries_max": 8 },
  "ledger": [
    { "id": 2,
      "tool": "compare_periods",
      "query": "$select=community_board,count(*)...&$group=community_board",
      "fetched_at": "2027-01-16T14:02:11Z",
      "result": { "total_a": 14200, "total_b": 18400, "pct_change": 29.6 } }
  ]
}

The loop

state = new_state(question)
while not state.over_budget():
    action = model(system_rules, state.summary(), tools)      # model decides
    if action.type == "final_draft":
        briefing = claim_check(action.text, state.ledger)       # code checks
        if briefing.ok: return briefing
        state.add_note(briefing.problems); continue             # one rewrite
    check = tool_gate.validate(action)                          # code checks
    if not check.ok:
        state.add_error(check.message); continue                # model sees the error
    result = run_with_retry(action, timeout=20, retries=1)
    state.ledger.append(result)                                 # result shapes next step
    trace.log(action, result)
return partial_briefing(state)                                  # budget reached

Failure handling

FailureHow it is detectedResponse
Data source timeoutNo response in 20 secondsRetry once with a narrower query, then report the source as unavailable. A broad query to this dataset timed out during our own check.
Gate rejects a callValidation errorThe error text goes to the model; it counts as a step
Zero resultsEmpty responseThe model must confirm coverage before saying "none"
Incomplete coverageMissing daysStop the comparison and show the gap
Budget reachedStep, query, or time capReturn partial findings, labeled as partial
Malformed model outputSchema check failsAsk once for a corrected call, then stop
Instructions inside record textNot detected; prevented by designRecord text is passed only as quoted data, and most tools return counts, not text

Security and privacy

  • Every tool is read-only. There is no write tool to misuse.
  • API keys stay in the harness; the model never sees them.
  • Only public data is used, and nothing is stored about the person asking.

Suggested stack

  • Python 3.12, an HTTP client, and the Anthropic API with tool calling
  • FastAPI serving one plain HTML page
  • SQLite for the ledger and a query cache
  • JSON Lines for traces
  • pytest for the test suite

5Build plan

In order. Each phase has an exit condition, and durations are rough estimates for one person.

Phase 0: SpikeHalf a day

Label and bbl coverage are already confirmed. Confirm how far back heat records go and a free weather source, then run three real queries.

ExitTwo real questions that need different follow-up steps.

Phase 1: Baseline1 day

Build the fixed pipeline with no agent: the same three queries and a template report.

ExitIt runs on every test question. This is what the agent must beat.

Phase 2: Agent loop2 to 3 days

Add the model-chosen next step, the four tools, the stop decision, the tool gate, and budgets.

ExitAt least three distinct tool sequences across the test suite.

Phase 3: Trust2 days

Add the evidence ledger, the claim check, and failure handling.

ExitZero unsupported claims across the test suite.

Phase 4: Production habits1 to 2 days

Add trace replay, run the test suite on every change, and write up the comparison with the baseline.

ExitEvery metric in section 3 is measured and reported.

Phase 5: Web page1 day

One page: a question box, the briefing with ledger references, the attached building list, and a collapsible trace of every step. The page calls the same harness the tests use.

ExitA person who has never seen the code can ask a question and follow every step the agent took.

LaterAfter v1
  • Review before sharing: a person approves a briefing before it goes to anyone else.
  • Scheduled watch: a weekly run during heat season that flags districts whose pattern changed.
  • Inspection data: a fifth tool over city inspection records, so findings can go beyond complaints.

Left out of v1 on purpose: memory across sessions, multiple agents, and a separate planning step. Each fixes a specific failure, so add one only after the traces show that failure.

7Open questions

Confirmed so far

  • The public 311 dataset is live, with records through October 5, 2026.
  • The complaint label is HEAT/HOT WATER: 216,699 complaints from January 1 to October 8, 2026.
  • bbl is filled in on 99.6% of those (215,916), so count_buildings will work.
  • Records carry an address, coordinates, a status, and a community board.
  • Broad queries can time out.
  • Heat season dates and indoor temperature rules, from the city's housing department.

To confirm in the spike

  • How far back heat records go. At least October 2025 to May 2026 is needed.
  • A free weather history source for New York City that code can reach.
  • That the build machine can reach the city's data site.
  • That real questions produce at least two different paths.

Decided 8 October

  • Model: Claude, through the Anthropic API. Cost cap per question set during the spike.
  • Addresses: counts in the briefing; building addresses in an attached list.
  • Interface: a simple web page showing the question, the briefing, and the trace.
  • Where it is built: Claude Code, from a project file that carries this spec.
